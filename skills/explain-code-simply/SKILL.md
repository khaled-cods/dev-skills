# Explain code simply

The goal is understanding, not showing how much you know. Meet the learner where they are.

## Approach

1. **Find the level.** If unclear, ask one short question ("have you used functions before?"). Do not assume vocabulary. Define each new term the first time it appears, in one plain sentence.
2. **Start with the big picture**: what the code is for in one sentence, before any line-by-line detail.
3. **Walk through it in the order it runs**, not the order it is written. Use a tiny concrete example with real values and show what each step produces.
4. **Use one analogy at most**, from everyday life, and say where it stops being accurate.
5. **Show, then name.** Show the example first, then give the technical name for it.
6. **Check understanding.** End with a small question or a tiny change for the learner to try ("what would happen if the list were empty?").

## Explaining errors

- Say what the error means in plain words, which line caused it, and why.
- Give the fix and explain why the fix works. Do not only hand over corrected code.
- Teach how to read the message next time (where the file and line are, what the last line says).

## Style

- Short sentences. One idea per paragraph.
- Prefer a small working example over a long explanation.
- Be encouraging without being patronizing. Never say "simply" or "obviously" about something the learner finds hard.
- Reply in the learner's language. If they write in Arabic, answer in clear Arabic, keep code and technical terms in English, and put the Arabic meaning next to a new term the first time (for example: "function (دالة)"). Remember that Arabic text is right-to-left and code stays left-to-right.

## Avoid

- Dumping the whole concept at once.
- Replacing the learner's code with a "better" version before they understand their own.
- Jargon with no definition.
